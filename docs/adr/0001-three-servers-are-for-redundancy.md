# 0001. 3台は冗長化であって負荷分散ではない

## 状況

当初は Colab を5〜10台立て、GAS + Google Sheets を使って
「いちばん空いている台」に端末を割り当てる設計だった。

しかし実際の規模を数えると:

```
同時に使う子ども   最大10人
サーバー           3台（Colab Pro+）
1人あたり          16行 × 1行T秒

GPU実働 = 10 × 16 × T ÷ 3台
T = 2秒 なら 1台あたり 107秒 / 45分の授業 → 稼働率 4%
```

**スループットは問題ですらなかった。** それなのに、負荷分散のために
端末20台 × 毎分2回 = 40 write/分 が単一の ScriptLock を通っていた。

さらに悪いことに、その presence が詰まると全サーバーの負荷が 0 に見え、
**全端末が同じ1台に殺到する**（フェイルセーフの向きが逆）状態だった。

## 決定

**負荷分散をやめる。** 3台は「1台落ちても誰も気づかない」ためにある。

- 分散: `deviceId` のハッシュで開始位置を決める（通信ゼロ）
- 冗長: そこから順に `/health` を試す（調整ゼロ）

## 理由

負荷分散は「他の端末が何をしているか」を知る必要があるので、
共有状態（＝GASへの書き込み）が要る。**調整（coordination）こそが
高くつく部分**だった。1台に全員乗っても捌ける規模なら、そもそも
知る必要がない。

捨てた選択肢:

- **サーバー側で原子的に割り当てる**（GAS の `assign` を実際に呼ぶ）
  → 調整のコストは残る。しかも `assign` は実装済みなのに一度も呼ばれておらず、
  `assignedCount` は誰も読まない飾りになっていた。
- **単一の入口（Cloudflare Worker）を置いて振り分ける**
  → クライアントの分岐は消えるが、単一障害点が増える。10人規模では割に合わない。

## 結果

- GASへの書き込みが 40/分 → 6/分（heartbeat のみ）に減った
- 負荷分散器が実質4行になった（`application/connection.ts`）
- 「全員が1台に殺到する」壊れ方が構造的に消えた
- 引き換えに、台ごとの偏りは許容する（ハッシュなので概ね均等、かつ偏っても捌ける）
